# Custom bot generation

Implemented with the saved Meta API key and `muse-image-1.0`. It does not change
the model used for task building or use the Muse CLI/subscription.

## Entry points

- New task: **Create a character** beside **Try another bot**.
- Saved task: **Customize character** on its My tools card.

## Flow and cost

1. Describe a character and approve a single preview (estimated US$0.01).
2. Inspect the preview. Reuse it immediately, start another design, or separately
   approve the remaining five poses (estimated US$0.05).
3. Each additional pose uses the preview as its reference through the images/edit
   endpoint. All six images are independent files, with no sprite-grid cropping.
4. Use the finished bot, or stop after the current image and resume from saved
   designs later. Completed poses are cached and never regenerated by a retry.

Prices are estimates based on Meta's published US$0.01/image rate checked on
2026-10-31: https://dev.meta.ai/docs/pricing-rate-limits
API contract: https://dev.meta.ai/docs/image-generation

## Persistence and behavior

Images live under the application data directory, `bots/<id>/<pose>.png`.
Metadata, completed poses, and request attempts are stored in the encrypted
application database. Assignment uses the existing local task-to-bot identity
mapping. The app loads image data through narrow IPC methods; no credentials or
filesystem paths go to the renderer. Displaying and animating cached images makes
no generation requests. Missing poses use the preview; missing custom assets
fall back to the built-in character.

Cloud admission, Local only, emergency stop, and removal of the key retain their
existing policy boundaries. Outbound generation intents and known image costs
appear in the existing privacy history. Deleting history keeps saved custom bots;
including tools in deletion removes their metadata and image directory as well.

Each design has a conservative 20-request (approximately US$0.20) budget, including
uncertain requests. One image request runs at a time. No paid request is retried
automatically. An interrupted/ambiguous request persists a warning and requires
explicit acknowledgment of a possible extra charge before retrying a pose.

Returned images are bounded, decoded as PNG, and checked for dimensions and memory
limits before storage. External image URLs and SVG are not accepted. Every generated image is saved as an original, then processed locally by the
bundled macOS Vision helper. Transparent outputs are validated and saved separately
as `<pose>-transparent.png`. No extra API request or charge is needed. If cleanup
fails, generation pauses and the saved original can be retried with **Remove
backgrounds · no API charge**, even in Local only mode. These are six expression poses with CSS motion, not video.

## Background removal validation

The existing single Muse bot JPEG was processed with the native helper and
inspected as a 1920×1280 RGBA cutout. No new generations were made. A focused Rust
check rejects opaque, empty, or resized outputs; the existing UI consent flow is
still covered. The bundled helper uses Apple Vision's foreground instance mask
and retains the original image extent. Foreground detection can fail, so the
original remains available and failures are shown rather than silently labeled
transparent.


## Character direction — minimal and cool

The preview prompt now separates the user's subject from shared visual guidance.
It defaults to a few intentional geometric forms, clean matte surfaces, balanced
proportions, understated facial marks, a restrained neutral palette with at most
one accent, and a calm confident pose. Babyish proportions, oversized eyes and
sugary pastel palettes are avoided unless the user explicitly requests a cute or
plush style. Explicit user appearance requests take
priority. Animals, plants, objects, creatures and robots are all valid; robot
anatomy and limbs are not added by default. Workflow descriptions can inspire a
simple mascot rather than appearing as text on the character.

Matching expressions use only the approved reference's features. The reference
branch does not apply the new simplifying style, so existing intricate characters
are preserved rather than redesigned. Storage IDs, prices, six-pose caching and
local transparency processing are unchanged. Product controls now say character.
No paid image calls were made for this implementation update.

The minimal/cool update changes new previews only. Existing approved characters
keep their reference appearance when generating additional poses. No paid image
generations were made for this prompt update.

## Selected robot face direction

New robot previews default to the approved oval-visor study: a simple matte
slate-style body, softly rounded cuboid head, understated inset dark face panel
and two luminous ivory oval eyes. Neutral eyes are fully open and attentive.
Explicit appearance requests still override these defaults. Non-robot characters
do not inherit the screen face, and additional poses preserve their approved
reference. Study: `output/slate-bot-eye-study/01-oval-visor.png`. This prompt update
makes no paid image requests.

## Preview reference correction

Preview generation now sends the bundled approved oval-visor image as a visual
style reference through the images edit endpoint. Task-only descriptions such as
“Rent” default to a robot, not a literal key or house. Explicit non-robot
descriptions retain their subject. Preview prompts distinguish style inspiration
from later poses' identity lock; later poses still use their own approved preview.
The studio disclosure names the built-in reference. No automatic regeneration or
paid retries occur, and saved designs are kept.

## Independent robot silhouettes

The preview reference now supplies face language only, with explicit instructions
not to copy its head, torso, limbs, palette or chest stripe. New design IDs receive
a stable mix of head shape, body proportions and restrained palette (216 brief
combinations). Explicit user appearance and non-robot anatomy take priority.
Additional poses remain locked to the approved preview, not the style image.
This update uses no paid generations.

## Glossy companion finish

The user clarified that the existing-bot resemblance means shiny surfaces. New
previews now request glossy ceramic or polished enamel, soft specular highlights
and studio reflections, with a glossy black face panel. This explicitly overrides
the matte style reference finish. Robot shape variation stays close to the
existing rounded, compact companion family. Explicit material requests still
take priority; later poses preserve their approved preview. No paid calls.

## Delete saved characters

The current preview and each saved-character row provide a Delete action with
an inline confirmation. Deletion removes original and transparent images plus
metadata/index entries, clears the image cache and task avatar assignments, and
keeps tasks intact with built-in avatars. Native deletion validates the UUID,
shares the image-generation lock, runs locally with cloud work paused and
updates metadata/index in one transaction. Failed deletion keeps the UI entry
available for retry. No paid API calls are made.

## Distinct, believable expression poses

Matching-pose prompts now explicitly preserve identity rather than the neutral
stance. Working brings existing hands forward with a downward attentive gaze;
waiting uses an upright curious tilt and relaxed stance; happy uses a small wave
and crescent eyes; concerned uses a reachable hand-to-face gesture and worried
eye shapes; resting lowers the body and closes the eyes. Every acting instruction
is conditional on existing anatomy, with natural joint limits and stable balance.
Existing cached poses remain unchanged and are never regenerated automatically.

## Description-led previews and compact creator

The creator puts the saved preview and its Use action first, with expressions,
saved characters, and generation details in expandable sections. Paid requests
still require separate approval with their estimated cost shown.

New preview prompts prioritize the user's subject, silhouette, anatomy, colors,
materials and style. The shared identity is the dark glass face panel and bright
ivory oval eyes; the supplied reference no longer constrains the body or palette.
Design IDs no longer inject competing preset anatomy or colors. Later poses
continue to preserve the approved preview. Existing saved artwork is unchanged.
