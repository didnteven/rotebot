# 13 — UI/UX design (primary UX track)

Author: planning agent, track 13 (Claude). Scope: the whole experience, macOS first, Windows notes.
Inputs: `plan/BRIEF.md`, the MSP v1 schema (`plan/reference/msp/msp.d.ts`), `muse --help`.
This file covers what the user sees and does. It leaves the capture, model and runtime design to
the other tracks, and names the places where those tracks have to give the UI certain data.

---

## 0. The three questions, answered up front

1. **Who is the user, and what state are they in?** A knowledge worker who has put something
   *watching their screen* on their computer. For the first week they are **suspicious**. After
   that they are **busy** and mostly ignore the app. When it finds something they are
   **curious but skeptical**. When a build runs they are **impatient**. When an automation acts
   for them they are **anxious about side effects**. Every screen below is designed for one of
   those five states.
2. **What is the one thing the product must let them do?** Go from "here's a tedious thing I
   do" to "a tool now does it, and I trust it" without writing code.
3. **What does the business need?** A first working automation within the first session
   (day-one value, through Teach mode). After that, a discovery the user agrees is real within
   about a week. Trust comes before engagement: an app that people uninstall on day two because
   it felt creepy has no funnel to optimize.

Wherever (1) and (3) conflict, the design favors (1). For example, notifications are rationed
even though more of them would mean more "engagement".

---

## 1. The five UX principles (they decide every tie)

| # | Principle | What it means in practice |
|---|-----------|---------------------------|
| 1 | **Show, then ask.** | Value before permission, evidence before suggestion, preview before action. No permission prompt without a sentence of "why" and a live demo. No opportunity without the observed steps. No automation run without a dry run being available. |
| 2 | **Nothing invisible.** | Everything captured, every byte sent to Meta, every file an automation touches, every command Muse wants to run can be inspected in at most two clicks. The menu bar icon always tells the truth about capture state. |
| 3 | **The user is the author.** | Macroscope proposes and the user decides. "No", "never for this app" and "delete" are each one click and permanent. Muse never gets broader permission than the user granted for that build. |
| 4 | **Quiet by default.** | Interrupt only when the interruption is worth more than the time it costs. Budget: at most one proactive notification a day, never during screen sharing or Focus. The app should feel like a good instrument, not a feed. |
| 5 | **Reversible, or loudly irreversible.** | Undo is the default safety mechanism, and confirmation dialogs are kept for things that really can't be undone (sending email, POSTing to an API, deleting captured history). Anything irreversible says so *before* the user commits. |

Principle 2 is the product's moat as much as a UX rule. Competitors in the "watch everything"
space ran into trust problems (Microsoft Recall's 2024 backlash is the reference case
[assumption: widely reported, not re-checked here]). If Macroscope is as legible as possible
about what it does, it can actually ship.

## 2. Visual direction

**Tone: "a quiet lab instrument."** Precise, calm, slightly technical, never cute. Think of
Activity Monitor crossed with Linear's restraint. No sparkle emoji, no purple AI gradients, no
"magic" language. The app watches people and writes code for them, and the visual tone has to
say *careful*.

| Dimension | Decision | Why |
|---|---|---|
| Platform look | Native AppKit/SwiftUI look on macOS: `NavigationSplitView`, source-list sidebar with `.sidebar` vibrancy material, toolbar with unified title, Settings window via ⌘, | A watcher app that looks non-native looks untrustworthy. Native also gets accessibility, dark mode and keyboard nav for free. |
| Density | Medium, similar to Mail or Xcode's navigator. 13 pt body (macOS standard), 11 pt captions, 20–22 pt page titles. Deliberately *not* the web-style 16 px body. | macOS's native body size is 13 pt. Bigger text reads as a web wrapper. |
| Type | SF Pro (system) for all UI, SF Mono for code, diffs, terminal and the payload viewer. Tabular figures for durations, costs and counts. Only four styles per screen: title, section header, body, caption. | One family, with weight doing the work. |
| Color | Greyscale UI. **Selection and controls use the user's system accent color** (Apple convention). Semantic colors only: green = time saved / test passed, orange = needs your attention / approval, red = failed / destructive / irreversible, and **one reserved "capture" color (systemTeal)** used only for "Macroscope is observing right now". | Color is meaning. Reserving one hue for capture lets users learn it is always visible. Every color is paired with an SF Symbol and a word (colorblind-safe). |
| Brand | The brand mark (a lens/reticle glyph) appears in the app icon, menu bar, and the empty-state illustrations. Nowhere else. | Branding inside a utility is noise. |
| Iconography | SF Symbols only, monochrome or hierarchical rendering, one weight (regular) throughout. | Mixed icon sets are the fastest tell of an unpolished app. |
| Redaction style | Redacted regions in thumbnails are **solid neutral bars with a small label** (`▇▇▇ email`), never blur. | Blur looks like it might be reversible and invites "can they unblur it?". Bars say "this is gone". |
| Motion | 150–250 ms, ease-out in, ease-in out. Only three things animate: the menu bar icon during Teach recording (pulse), the build stepper advancing, and new transcript items sliding in. Streaming text appears in whole lines or sentences, not as character typewriter jitter. All motion is disabled under Reduce Motion. | A watcher that is constantly moving feels like it is constantly *doing* something to you. |
| Dark mode | First-class. Elevation through lightness, desaturated semantic colors. Thumbnails get a 1 px separator so dark screenshots don't bleed into dark UI. | Many target users (developers, ops people) live in dark mode. |

**Implementation note for the stack decision (other tracks):** the menu bar extra, the
onboarding permission checks and the notification actions must be native (Swift) on macOS
whatever UI toolkit the main window uses. If the main window is Flutter, use `macos_ui`-style
widgets and native vibrancy through a platform view, and accept that the sidebar will feel
95% native rather than 100%. **[assumption]** Recommendation from a UX point of view: SwiftUI on
macOS, WinUI 3 on Windows, sharing a core. I'm aware that this costs a solo developer two UI
codebases, and I'm deferring that call to the architecture tracks (11/12).

## 3. First run and permissions onboarding

### 3.1 Flow

```
 [1 Welcome] → [2 How it works] → [3 Choose observation level] → [4 Exclusions (pre-filled)]
      → [5 Permissions, one at a time, each with live preview] → [6 Connect Muse + API key]
      → [7 "What Macroscope sees" live check] → [8 Done: Teach your first task / Just watch]
```

Eight steps sounds like a lot, but steps 2–4 are each a single decision, and the user can go
back from every step. The user can stop after step 5 and finish 6 later (building needs Muse,
watching does not). Progress is shown as dots, not "Step 3 of 8", because the count invites
quitting.

## 4. Always-on presence (menu bar extra)

### 4.1 Icon states

One template-image glyph (a reticle/lens), with state shown by **shape changes** (not just
color), so it works in monochrome menu bars and for colorblind users.

| State | Glyph | Animation | Meaning |
|---|---|---|---|
| Observing | `◎` reticle, solid | none | Capture on, nothing pending |
| Paused | `◎` with diagonal slash | none | User paused, or auto-paused (sharing, excluded app, locked) |
| Analyzing | `◎` with a small 3-dot overlay at bottom right | none (static) | Local pattern pass or a model request in flight |
| Building | `◎` with a small progress arc | arc fills, no spin | A Muse session is active |
| Needs you | `◎` with orange dot | none | Approval pending or a build is blocked |
| Found something | `◎` with accent dot | none | New discovery not yet seen |
| Teaching | `●` red record dot replaces reticle | slow 2 s pulse (off under Reduce Motion) | Teach recording in progress |
| Problem | `◎` with `!` | none | Permission revoked, Muse missing, key rejected |

Precedence when several apply: Teaching > Problem > Needs you > Building > Found > Analyzing
> Paused/Observing. "Analyzing" can be switched off in Settings for users who find it noisy.

### 4.3 Global hotkeys (defaults, all rebindable in Settings › Shortcuts)

| Action | macOS | Windows |
|---|---|---|
| Pause / resume observing | ⌃⌥⌘P | Ctrl+Alt+Shift+P |
| Start / stop Teach | ⌃⌥⌘T | Ctrl+Alt+Shift+T |
| Open quick menu | ⌃⌥⌘M | Ctrl+Alt+Shift+M |
| Delete the last 15 minutes | ⌃⌥⌘⌫ (shows a 5 s undo toast) | Ctrl+Alt+Shift+Backspace |

"Delete the last 15 minutes" is the panic button: "I just looked at something I shouldn't
have had recorded." It removes the frames and events, and Undo is available for 5 seconds
(principle 5).

Pause feedback: a small HUD (like the macOS volume HUD) reading "Observing paused · ⌃⌥⌘P
to resume", plus the slashed icon. Resume shows the same HUD. Pause is never silent.

### 4.4 Teach mode

```
 Start (hotkey or button) ─► 3-2-1 HUD ─► recording (red icon + floating mini-bar)
                                              │
            ┌─────────────────────────────────┴──────────┐
            │  ● Teaching  02:14   [ Add note ]  [ ■ Stop ]│  ← draggable, stays on top,
            └────────────────────────────────────────────┘    excluded from its own capture
```

During Teach mode, capture fidelity goes up (every UI change, not sampled), and exclusions

That note is the most valuable input the builder gets.

### 5.2 Why this IA

The sidebar follows the **lifecycle of a piece of work**: *found → built → running*, plus two
supporting views (*evidence* and *control*).

- **Discoveries** is an inbox, like Mail: triage-oriented, with a count of unseen items. The
  inbox metaphor matters. Users already know items can be archived, dismissed and snoozed, and
  that an empty inbox is a good state, not a failure.
- **Automations** holds the things the user owns. Discoveries are Macroscope's ideas and
  Automations are the user's tools, so the line between them is about ownership. Mixing them
  makes it unclear what is "mine".
- **Builds** gets its own section, instead of being a modal inside an opportunity, because
  builds take minutes, run in the background, can stall on approvals and get repaired later.
  Users need somewhere to go back to. Each build can also pop out into its own window
  (⌘⇧O), like a document, for people who want it on a second display.
- **Activity** is the evidence timeline (what was observed, day by day). Most users rarely
  visit it, but it is what makes "Nothing invisible" true, and every opportunity's evidence
  deep-links into it.
- **Privacy** is a top-level section, **not** a Settings tab. In this product, privacy *is*
  the product: being one click away all the time signals that, and the request log changes
  daily, so it isn't configuration. Configuration that rarely changes (hotkeys, budget, Muse
  path) goes in the standard **Settings window (⌘,)**, following macOS convention.

Rejected alternative: a single chat-first window ("ask Macroscope anything"). Chat hides
state. The user's real questions ("what did you find, what's running, what did you send") are
answered better by lists than by conversation. Chat stays where it belongs, inside a build.

### 5.3 Settings window (⌘,)

Toolbar tabs, macOS style: **General** (launch at login, menu bar options) · **Observation**
(level ladder from §3.3, sampling) · **Muse & API** (binary path and version, key, model,
budget, reasoning effort default) · **Notifications** · **Shortcuts** · **Advanced** (data
folder, logs, local-only mode, reset onboarding).

Design notes:

- **Title is a verb phrase in the user's words**, generated from the steps. Never "Workflow #12".
- **Time saved shows its arithmetic.** An unexplained "saves 1.6 h" reads as marketing, and a
  visible formula reads as a measurement. If the estimate is shaky, the confidence line says why.
- **Confidence is a word plus a reason**, never a percentage. "73%" looks precise but tells the
  user nothing they can act on.
- **Evidence thumbnails** are redacted crops around the active region (not full screens), with
  step text beside them. Clicking a thumbnail opens it large, in the Activity timeline context.
  "Session ▾" switches between the 7 observed occurrences, which is how users check that it
  really is the same task.
- **"Edit steps"** lets the user correct the pattern (merge, delete, mark "this varies") before
  building. Correcting before building is much cheaper than repairing afterwards.
- **"Not useful ▾"** opens a one-click reason list: *Already automated* · *Not actually
  repetitive* · *Too rare to matter* · *I want to do this myself* · *Steps are wrong* ·
  *Other…*. The reason feeds the pattern engine (track 09) and the item disappears with a 5 s
  Undo.
- **"Never suggest for Jira"** is deliberately a text-style button behind the overflow-adjacent
  position. It's permanent and broad, so it shouldn't be hit by accident, but it's still one
  click. It adds a rule visible in Privacy › Exclusions with an Undo toast.

### 7.1 Layout

A three-region split view: transcript on the left (primary), inspector on the right (tabs), and

Mapping from the protocol to the UI ([local: MSP v1 schema]):

| MSP | UI |
|---|---|
| `item/started/delta/completed` with `ItemKind` `agentMessage` | ◆ Muse prose block, streamed in sentence-sized chunks |
| `reasoning` | "▸ Thinking · 12 s" collapsed by default |
| `toolCall` (file edit) | ✎ file row with +/− counts, click opens the diff in the Files tab |
| `toolCall` (shell) | ▸ Ran `cmd` with ✓/✗ and collapsible output |
| `session/todoListChanged` (`TodoItem.status`, `activeForm`) | Plan tab checklist. `activeForm` drives the "◐ Writing …" label |
| `approval/requested` | Approval card (§7.3), pinned |
| `session/tokenUsage` / `usage/changed` | $ meter in the status bar |
| `turn/completed` with error `authRequired` / `QuotaDetail` | Error banners (§10) |
| `subagent` items | Nested, indented group with the subagent name |

The top stepper (Planning → Writing → Testing → Ready) is **derived by Macroscope**, not
reported by Muse. Planning means no file edits yet, Writing means edits are happening, Testing
means test commands are running, and Ready means the final turn completed with tests passing.
Being derived keeps it honest even if Muse's own todo list is sloppy.

### 7.2 Inspector tabs

**Files:** a tree of the build's worktree with modified markers, plus a side-by-side diff
(SF Mono, syntax-colored, word-level highlights). On the first build every file is new, so the
default view is "file", with a toggle to "diff vs. previous version". Diff-vs-previous is the
default for repairs.

```
 Files                                 │ to_csv.py                      new file · 31 lines
 ▾ weekly-status/                      │  1  import csv, datetime
     ● fetch_jira.py          +48      │  2
     ● to_csv.py              +31      │  3  def fmt(d: str) -> str:
     ◐ mail_draft.applescript          │  4      return datetime.date.fromisoformat(d)
     ○ tests/                          │  5          .strftime("%b %-d")
     macroscope.json  (manifest)       │  …
```

**Tests:** results as a list (✓/✗, duration). A failed test expands to show the assertion and
a "Show Muse this failure" button, which is pre-filled steer text. The fixtures are generated
from the redacted evidence, so the user sees "tested on data shaped like your Oct 21 session".

**Output:** a sandbox dry run of the finished tool (see §8.1), available once Ready.

### 7.3 Approval cards ("needs approval" state)

Approvals are the most safety-critical UI in the product. Per the schema, an approval has a
`subject.kind` of `shell | fileAccess | network | unixSocket | process | tool`, and
`availableChoices` each carry a `scope` (`once | session | localPersistent`), and some carry
`acceptsFeedback`. **There is no dismiss-without-deciding on the wire**, so a pending
approval stays visible until it is decided [local: msp.d.ts, approval/request doc comment].

```
┌──────────────────────────────────────────────────────────────┐
│ ⚠  Muse wants to connect to the internet                     │
│                                                              │
│    api.atlassian.net  · HTTPS                                │
│    To test fetch_jira.py against your real Jira.             │
│    ✓ This domain appeared in your recorded workflow.         │
│                                                              │
│    [ Allow once ]   [ Allow for this build ]   [ Deny… ]     │
│    Always allow api.atlassian.net ›          (rule preview)  │
└──────────────────────────────────────────────────────────────┘
```

Rules for approval cards:

- **Headline in plain language by kind:** shell → "wants to run a command", fileAccess →
  "wants to read/write <path>", network → "wants to connect to <host>", process/tool →
  "wants to use <tool>". Unknown kinds get a generic card showing `rawArgs`, and are **never
  auto-approved** (the schema says this explicitly).
- **The command or path is shown verbatim in SF Mono.** Multi-stage commands
  (`subject.stages`, for example a pipe) show "Step 1 of 2" with each argv, so the user
  approves what will actually run.
- **Provenance check (prompt-injection defense, UX layer):** for network hosts and paths,
  show ✓ "appeared in your recorded workflow" or ⚠ **"never seen in your workflow"**. A build
  that suddenly wants `pastebin.com` after reading screen text is the attack this catches.
  Text on a user's screen is untrusted input, and this badge is the user's tripwire.
- **Button order:** the narrowest scope ("Allow once") comes first and widest last. The
  `localPersistent` choice is a secondary link, with its `rulePreview` shown, never a big button.
- **"Deny…"** opens a feedback field when `acceptsFeedback` is true ("use the CSV export
  instead"). Denial with a reason is how users steer.
- **Placement:** the card is inline in the transcript **and** pinned at the top of the
  transcript while pending. The stepper shows "● Needs you". The menu bar shows the orange
  dot, and if the Builder window isn't key for more than 30 s, a notification fires with
  "Review" (not "Allow" — approvals are never granted from a notification banner).
- **Subagent approvals** (`subagentOrigin`) say "from helper: <name>" so the user knows which
  part of the work is asking.

### 7.4 Raw terminal toggle (power users)

⌘⇧T flips the transcript region to a PTY running the Muse TUI on the **same session**
(`muse resume <session-ref>` in the build's worktree, with the key in the environment).

**[assumption — verify with track 04]:** whether a `muse serve` host and a TUI can attach to one
session at the same time. Safe UX either way: while the terminal is active, the structured
view becomes **read-only** with a banner "Controlled from terminal — switch back to steer here".
That way two drivers never compete. On switching back, Macroscope re-reads the session
(`session/read`) and rebuilds the transcript. The terminal uses SF Mono 12 pt, follows the app
theme, and has a "Copy session id" item in its menu.

```
│                                                                                  │
```

```
│                                                                                  │
│ HOW MUCH TO ASK YOU                                                              │
│  (•) Ask before each run   ( ) Run, then tell me   ( ) Run quietly               │
│  Suggest "Run, then tell me" after 5 clean runs.                                 │
│                                                                                  │
│ RECENT RUNS                                                                      │

└──────────────────────────────────────────────────────────────────────────────────┘
```

- **"What it can do" is generated from the enforced sandbox profile**, not from Muse's
  description of itself. The ✕ line (what it *can't* do) matters as much as the ✓ lines.
  If the runtime can't enforce a ✕, the UI must not claim it.
- **Trust ladder** ("how much to ask you") starts at "Ask before each run" for every new or
  repaired version. Promotion is suggested, never automatic.
- **Undo** exists per run for effects the runtime snapshotted (created/replaced/moved files,
  drafts). Effects that can't be undone (sent mail, API POST/PUT) are marked **⚠ can't be
  undone** in "What it can do", and under the default ladder they require a confirmation sheet
  every time, listing the exact irreversible effects (principle 5).
- **Run log** shows plain-language steps with timestamps, plus a "Raw output" disclosure
  (stdout/stderr, SF Mono). Secrets are masked in logs.

### 8.3 Failure and "Repair with Muse"

A failure notification (only for unattended runs) reads: *"Weekly status CSV didn't run —
Jira rejected the token. [Fix token] [Repair with Muse]"*. The plain-language reason comes
from a small classifier (auth / network / changed UI or API / bug) and **leads with the
cheapest fix**. A rejected token doesn't need an AI repair, it needs a token field.

"Repair with Muse" opens a Builder session pre-loaded with the failing log, the previous green
run's log, the current source, and a brief: "Fix this failure without widening permissions."
It shows a diff against the current version. On Ready, the result becomes v3, goes back to
"Ask before each run", and keeps v2 for one-click rollback. If the repair needs *wider*
permissions, the approval card says so explicitly: "This repair asks for more than v2 had."

## 10. Empty states, notifications, errors

### 10.1 Empty states (the empty state *is* onboarding)

| Where | Copy | Action |
|---|---|---|
| Discoveries, day 1–4 | "Still learning your routine. Observed 6 h 12 m across 9 apps so far. Patterns usually show up after 3–5 days." plus a small progress bar of observed hours (honest, not gamified) | **Teach a task** · See what's been observed |
| Discoveries, all triaged | "Inbox clear. We'll add things as we spot them." | none (an empty inbox is a success state) |
| Discoveries, after 2 weeks with nothing | "Nothing repetitive enough yet. That can mean your work varies a lot, or that we're excluded from the apps where the repetition happens." | Review exclusions · Teach a task |
| Automations | "Tools Macroscope builds for you live here. Start from a discovery, or teach a task." | Go to Discoveries · Teach a task |
| Builds | "No builds yet. Builds start when you choose Automate this." | none |
| Activity, paused all day | "Observing was paused today." | Resume |
| Sent to Meta | "Nothing has been sent to Meta yet." (said with pride; this is a feature) | none |

### 10.2 Notifications (rare and valuable)

Budget: **at most one proactive notification per day** (discoveries). Transactional
notifications (approvals, failures of unattended runs, permission problems) are exempt, because
the user is waiting on them or would be hurt by not knowing.

| Notification | When | Actions |
|---|---|---|
| New discovery | High confidence AND ≥ 30 min/month saved, batched into a daily digest at the user's chosen time (default 16:30, end of the working day, when a suggestion is least disruptive) | View · Not now |
| Build needs approval | Builder window not focused for 30 s | Review (opens card; never "Allow" from the banner) |
| Build ready | Build finished while the window was in the background | Dry run |
| Automation failed | Only for scheduled/unattended runs | Fix / Repair with Muse |
| Automation ran | Only at trust level "Run, then tell me" | Undo · View |
| Observing stopped | Permission revoked or capture crashed | Fix |

Never sent: "analyzing…", "we found nothing", streaks, weekly "you saved X hours!"
celebrations (that goes in the app, not as a push). Suppressed entirely during screen sharing,
Focus modes (unless the user allows Macroscope through), and full-screen presentations.

```
 │ Your automations still run.                                              │
 │ [ Turn it back on… ]  (opens System Settings › Privacy › Screen Recording)│

```

| Error | Signal | Where shown | Degrades to |
|---|---|---|---|
| Muse missing / too old | binary not found, `muse --version` < min | Builds section banner, Settings › Muse | Discoveries only |
| Key missing / rejected | `TurnErrorKind = "authRequired"` [local: msp.d.ts] | Banner in the Builder + menu bar "!" | Builds paused |
| Rate limited | `QuotaDetail.resetsAtMs` [local: msp.d.ts] | Banner with the reset time, auto-resume | Build queued |
| Budget reached | Macroscope's own meter | Banner with "Add $X" | Build paused, files kept |
| Permission revoked | TCC check on a timer + capture failure | Menu bar "!" + one notification + banner | Next-lower observation level |
| Disk low | free space < 5 GB | Banner in Privacy | Screenshot capture paused, events continue |
| Model unavailable / unknown model id | `modelError`, `session/modelRouteUnserved` | Builder banner with "Switch model ▾" | Build paused |

Rule: **an error never discards user work.** Steer text, brief edits and built files survive
every failure.

## 13. Risks that can kill the product (UX lens)

1. **The creepiness cliff.** If the first impression is "this is spyware", nothing else matters.
   Mitigation: the observation ladder, pre-filled exclusions, the live mirror, the Sent-to-Meta
   log, and the panic hotkey. All of these ship in v1 and none of them gets cut for scope.
2. **The empty first week.** Mitigation: Teach mode as a first-class day-one path, plus an
   honest learning-progress empty state.
3. **macOS permission friction.** Screen Recording needs a relaunch, and recent macOS versions
   periodically re-confirm screen-recording access for apps that capture continuously
   **[assumption: Sequoia introduced recurring confirmations; verify current cadence and
   whether ScreenCaptureKit-based persistent capture is affected]**. If the OS asks the user
   "do you still want to allow this?" every few weeks, our own UI has to be ready to explain
   it, so we pre-warn in onboarding. The capture track should confirm.
4. **Approval fatigue makes people click "Always allow".** Mitigation: narrow scopes first,
   no shortcut for persistent rules, provenance badges, and a sensible Muse sandbox posture so
   fewer approvals are needed in the first place (fewer, more meaningful prompts).
5. **Prompt injection through screen contents.** Screen text flows into the build brief. UX
   mitigations: briefs show evidence as quoted data, "never seen in your workflow" warnings on
   network/path approvals, and declared permissions enforced by the runtime rather than
   described by the model. (The real defenses belong to tracks 08/10.)
6. **Surprise cost on the owner's key.** Mitigation: per-build and monthly budgets, a live $
   meter, and a cost column in the request log.
7. **Over-promising privacy copy.** Every privacy sentence in the UI is a contract. Before
   ship, each claim in §3 and §9 needs a test proving it (for example, "a screenshot never
   leaves the Mac unless it appears in the request log").

## Open questions for the owner

1. **Do screenshots ever leave the Mac outside of a build you started?** The onboarding copy
   (§3.5) assumes "no: pattern analysis uses local or text-only summaries". If the pattern
   engine needs to send frames to Muse models, the trust story changes and the copy must say so.
2. **Native UI per platform (SwiftUI + WinUI) or one cross-platform UI (Flutter/Tauri)?**
   From a UX standpoint native wins clearly for a watcher app. It costs you a second UI
   codebase that you can't test on Windows.
3. **Default observation level:** Standard (screenshots), as recommended, or Light, with
   screenshots as an opt-in upgrade later? Light is gentler but produces much weaker discoveries.
4. **Is Teach mode in v1?** I've made it the day-one value path. Cutting it means accepting a
   silent first week.
5. **Default monthly budget for Meta API usage** (I used $20 as a placeholder).

## Decisions I made

- Five governing principles: Show then ask · Nothing invisible · User is the author · Quiet by default · Reversible or loudly irreversible.
- Visual tone is "quiet lab instrument": native macOS, system accent for controls, one reserved capture color, SF Symbols only.
- Redaction is rendered as solid labeled bars, never blur.
- Onboarding uses an observation-level ladder (Light/Standard/Detailed) mapped to specific OS permissions.
- Exclusions are pre-filled and set before any permission is granted.
- A live "What Macroscope sees" mirror appears in onboarding and stays available from the menu bar.
- Teach mode is the first-class day-one path to a first automation.
- The menu bar icon uses shape-based states with fixed precedence, and only Teach mode animates.
- Four global hotkeys, including "Delete last 15 minutes" with undo.
- Sidebar IA: Discoveries / Automations / Builds / Activity / Privacy; Privacy is top-level, not in Settings.
- No chat-first main window; chat lives only inside builds.
- Opportunity detail shows the time-saved arithmetic and confidence as a word plus a reason (no percentages).
- An editable build brief, showing exactly what will be sent to Meta, sits between "Automate this" and Muse.
- The brief's "Must" constraints become both prompt constraints and declared automation permissions.
- The Builder is a transcript of structured MSP items plus Plan/Files/Tests/Output tabs; the stepper is derived by Macroscope.
- Approval cards have plain-language headlines, narrowest scope first, persistent rules as a secondary link, provenance badges, and are never approvable from a notification.
- The raw terminal is `muse resume` in a PTY, and the structured view is read-only while it is active.
- Dry run is the primary action at Ready, and "What it can do" is generated from the enforced sandbox profile.
- A trust ladder (Ask each run → Run then tell → Quiet) resets on every new version.
- Repair leads with the cheapest fix and creates a new version with rollback.
- Every model request is logged locally before sending, with a payload viewer and "add a rule" from leaks.
- Retention is set per data class, and "Delete everything" is the only typed confirmation.
- Proactive notifications are capped at one a day, as a digest, and suppressed during sharing or Focus.
- On Windows: tray flyout, a taskbar-pinning onboarding step, explicit consent screens in place of TCC, and the terminal toggle behind Advanced.
